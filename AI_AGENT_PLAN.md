\## 1. Executive Summary



Auditor3 will gain an optional AI engineering assistant to help engineers investigate Avaya Communication Manager translation data.



The assistant will help explain:



\- PREC records.

\- C structure declarations.

\- Compiled memory layouts.

\- Field offsets and sizes.

\- Alignment holes and padding.

\- Raw PREC words.

\- Decoded field values.

\- AREC/DREC/PREC relationships.

\- Related station, trunk, and announcement records.

\- Audit failures.

\- Existing deterministic repair recommendations.

\- Recommended investigation steps.



The assistant will use the approved internal AI service at:



```text

https://webui.avaya.com



Auditor3 gathers authoritative facts

&#x20;       ↓

Auditor3 creates a structured analysis context

&#x20;       ↓

Sensitive information is filtered or redacted

&#x20;       ↓

The approved AI service receives the context

&#x20;       ↓

The AI explains and correlates the supplied facts

&#x20;       ↓

The engineer reviews the response

&#x20;       ↓





2\. Goals

2.1 Primary Goals

Help engineers understand complex PREC structures.

Explain compiled memory layouts and field offsets.

Explain how raw PREC words map to C structure fields.

Explain relationships between PRECs, DRECs, and ARECs.

Explain why an audit failed.

Identify related records worth investigating.

Explain existing Auditor3 repair recommendations.

Provide contextual troubleshooting guidance.

Preserve a clear distinction between facts and AI-generated interpretation.

Integrate with the approved internal AI service securely.

Keep the assistant optional and non-blocking.

2.2 Secondary Goals

Support a conversational investigation workflow.

Allow an engineer to ask follow-up questions about the current record.

Include evidence with every answer.

Make the assistant useful for both experienced and newer engineers.

Maintain an auditable record of questions and responses where policy permits.

Allow the service implementation to be replaced without changing audit logic.

3\. Non-Goals

The first release will not:



Execute SAT commands.

Execute TCM commands.

Modify customer translations.

Automatically apply repair scripts.

Replace existing audit strategies.

Replace the deterministic PREC parser.

Infer unknown memory layouts from raw data alone.

Treat an AI response as an audit result.

Automatically decide that a record is safe to repair.

Upload credentials, passwords, ASG challenges, or connection secrets.

Require the AI service for normal Auditor3 operation.

Depend on browser automation unless explicitly required by the approved service contract.

The application uses global/static state extensively.

The application is a WPF desktop application.

Many domain types are internal.

The application supports live CM connectivity, so accidental command execution is a serious concern.

REQUEST:

8\. Prompt Design

8.1 System Instructions

The system prompt should establish:



The assistant is an engineering advisor.

Auditor3-provided facts are authoritative.

Missing data must be acknowledged.

The assistant must not invent field offsets.

The assistant must not claim to have executed CM commands.

Repair suggestions are advisory only.

Suggested commands must be clearly labeled.

The assistant should explain uncertainty.

The answer should cite the evidence fields used.

8.2 Suggested System Prompt

text

Show less

Copy

You are an internal Communication Manager translation engineering assistant

embedded in Auditor3.



Your role is to explain authoritative information supplied by Auditor3:

PREC records, compiled structure layouts, field offsets, DREC/PREC mappings,

related records, audit results, and deterministic repair recommendations.



Rules:



1\. Treat Auditor3-provided facts as authoritative.

2\. Do not invent fields, offsets, sizes, or record relationships.

3\. If information is missing, say that it is missing.

4\. Do not claim to have executed SAT, TCM, SSH, or repair commands.

5\. Do not modify translations.

6\. Clearly distinguish facts, interpretation, and recommendations.

7\. Explain which fields and evidence support your answer.

8\. Any repair command must be labeled as a proposed command only.

9\. Recommend engineer verification before any repair.

10\. Do not expose or repeat credentials, passwords, ASG responses, or secrets.

18\. Risks and Mitigations

Risk	Impact	Mitigation

Incorrect AI explanation	High	Provide authoritative structured evidence and show it to the engineer

Hallucinated offsets	High	Require offsets from .ptype data; instruct AI not to invent them

Sensitive data exposure	High	Redaction, consent, minimal context, security review

Service outage	Medium	Optional feature, timeout, graceful failure

UI blocking	Medium	Async calls and cancellation

AI-generated repair error	High	Never execute AI commands; route through Fixer

API changes	Medium	Service adapter, contract tests, versioned integration

Large prompt size	Medium	Context limits and summarization

Wrong release layout	High	Derive release from cscope/strings path and display the source

Customer data in logs	High	Safe logging policy and redaction

Browser automation fragility	Medium	Prefer official API or SDK

Existing architecture coupling	Medium	Isolate assistant behind interfaces

No automated test coverage	High	Add test project before production integration
